    60→    60→## 1. Source authorization, API terms, and applicable content licensing
    61→    61→
    62→    62→**Policy mapping (roadmap checklist item 1).** The proposed provider serves content category
    63→    63→**POLICY.md §3.1 (public-domain content)** and §3.2 (CC-licensed content), with the API itself falling
    64→    64→under §3.4 ("services whose APIs and terms of service permit the intended use"). It matches the
    65→    65→roadmap's Phase 3 build order #1 and the D3-approved initial source set. A new decision record
    66→    66→(**D20**, §11) is required before any code.
    67→    67→
    68→    68→**What the Archive itself says about rights (E6, E7 — VERIFIED quotes):**
    69→    69→
    70→    70→- "The Internet Archive does not make guarantees as to the copyright status of items on archive.org
    71→    71→  and cannot guarantee information posted on item details or collection pages regarding copyright or
    72→    72→  other intellectual property rights."
    73→    73→- The Terms of Use "require that users make use of the Internet Archive's Collections at their own
    74→    74→  risk and ensure that such use is non-infringing and in accordance with all applicable laws."
    75→    75→- For movies specifically: rights "vary from movie to movie but many of the films are licensed with
    76→    76→  Creative Commons Licenses" (uploader-designated), and "Archive.org cannot guarantee the accuracy of
    77→    77→  uploader-provided information."
    78→    78→
    79→    79→**Consequence for us (design constraint, not a claim):** item-level rights status is heterogeneous
    80→    80→and uploader-asserted. The provider therefore cannot rely on "it is on archive.org" as a rights
    81→    81→basis, and **a collection-level allowlist alone is NOT sufficient** — membership in a public-domain
    82→    82→collection does not make every item in it public domain (IA collections mix works, and rights
    83→    83→metadata is uploader-asserted of varying quality, E6/E7). The rights posture is two-layered:
    84→    84→
    85→    85→1. **Collection pool (necessary, not sufficient).** Curated public-domain collections bound what
    86→    86→   the search layer may surface at all (exact marker fields INFERRED, pinned by fixtures per §9).
    87→    87→2. **Per-item rights register (mandatory).** Only individually approved item identifiers may be
    88→    88→   served. Each register entry records: the identifier; the rights evidence actually reviewed
    89→    89→   (e.g. publication date/pre-copyright status, copyright-renewal research, the item's
    90→    90→   `licenseurl`/CC pointer and restricted-rights markers); the concluded permission scope (e.g.
    91→    91→   "public domain — no restrictions" or "CC BY — attribution as specified"); attribution
    92→    92→   requirements; the review date; and the reviewer. Uploader-provided license metadata (CC logos,
    93→    93→   `licenseurl`, rights fields) is **evidence to review, not an automatic guarantee** of ownership
    94→    94→   or permission (E6/E7 explicitly disclaim it). The register lives in
    95→    95→   `docs/evidence/ia-rights-register.md`; `load()`/`loadLinks()` must refuse any identifier absent
    96→    96→   from it (defense in depth on top of search filtering). IA's referenced public-domain film list
    97→    97→   (E7) is itself explicitly no-guarantee: it may inform review, never replace it.
    98→    98→
    99→    99→**API terms for automated access (E5, E4 — VERIFIED):** the Archive publishes a Bots/LLMs/Automated
   100→   100→Access policy requiring descriptive User-Agent identification and qualitative rate-limiting
   101→   101→discipline (§7), and documents public, unauthenticated read access to metadata ("most information
   102→   102→returned by Metadata Read is publicly available", E4). No clause prohibiting read-only API search or
   103→   103→metadata retrieval for a client application was found in the official pages captured this session.
   104→   104→**However — and this gate is preserved — the public accessibility of an API, and its non-exclusion
   105→   105→by robots.txt (E24), do NOT establish that every proposed application use is permitted.** The full
   106→   106→current Terms of Use could not be captured (E20); its archived dated copy is **action A1**, and the
   107→   107→ToU review — not robots.txt, not API availability — is the authority on permission (mirrors the
   108→   108→roadmap rule that ambiguity must be resolved, or the provider does not ship).
   109→   109→
   110→   110→**Out of scope from minute one (POLICY §3 prohibitions, D7/D8):** lending / controlled-digital-lending
   111→   111→items and any content requiring an archive.org account (E22), torrent/magnet delivery (excluded from
   112→   112→our `PlaybackLinkType` v1), and any DRM-protected item (none exists in IA public video, but the gate
   113→   113→is stated anyway).
   114→   114→
   115→   115→**Tag summary for §1:** authorization category VERIFIED (D3/POLICY); terms permitting read-only API
   116→   116→use UNRESOLVED — pending the ToU snapshot (E20/A1 gate); content licensing per-item
   117→   117→UNKNOWN-with-mitigation (collection pool + mandatory per-item rights register).

   193→   193→## 4. Item → movie / series / episode mapping in our data model
   194→   194→
   195→   195→IA's model (E3, VERIFIED): an **item** (identifier) is a directory of files with metadata; a
   196→   196→**collection** groups items; there is no native "series/season/episode" object for movies.
   197→   197→
   198→   198→Planned mapping (INFERRED — a design decision for D20, not an IA fact):
   199→   199→
   200→   200→- **Item = one work.** A curated public-domain film item → `MovieLoadResponse` with a single
   201→   201→  `dataUrl`. This is the v1 scope and the only mapping with an approved rights story (§1).
   202→   202→- **Multi-part items (INFERRED, deferred):** some items contain several independently titled video
   203→   203→  files (e.g. serial episode reels). The contract supports this as `TvSeriesLoadResponse` with one
   204→   204→  `Episode` per playable file (`Episode.data` = the same JSON blob; `name` from the file's `title`
   205→   205→  if present). This mapping is **not** in the initial scope; it is recorded here so the data
   206→   206→  contract (opaque `Episode.data`) will not need to change if approved later.
   207→   207→- **Collection = not a series object.** A collection (e.g. a curated PD set) can drive a homepage
   208→   208→  row via scrape/advancedsearch, but we do **not** model collections as `TvSeriesLoadResponse`
   209→   209→  bundles — IA collections mix works, are not ordered, and have no season/episode semantics.
   210→   210→- **Anime/dub/live variants:** not applicable; IA provides none of these semantics for our curated
   211→   211→  set. `tvTypes` for this provider = `['Movie', 'Documentary']` (constant, documented).
   212→   212→
   213→   213→Guard-rail: `Episode.data`/`dataUrl` stays opaque to the host (verified contract semantics);
   214→   214→only the provider decodes it.

   218→   218→## 5. Availability of direct MP4 / HLS playback URLs and browser-playback verification
   219→   219→
   220→   220→**What is verified (E8, E7):** IA generates **web-friendly h.264 MP4 derivatives** for video items
   221→   221→("We will derive other file formats that are web-friendly such as h.264 mp4"), and the Archive's own
   222→   222→help explicitly acknowledges that some files "simply can't be streamed" and fall back to download.
   223→   223→So the officially documented playback path is **progressive MP4 of a derivative file** — exactly the
   224→   224→`PlaybackLink.type: 'video'` shape our Phase 4 player maps to native `<video>`. (Byte-range support
   225→   225→on the file hosts is itself NOT verified — E17, probe P2b; it is a playback prerequisite, not part
   226→   226→of what IA documents.)
   227→   227→
   228→   228→**Direct URL form (INFERRED, E15):** `https://archive.org/download/{identifier}/{fileName}` for the
   229→   229→h.264 derivative selected from `files[]`, likely 30x-redirecting to a datanode
   230→   230→(`ia{NNN}.us.archive.org` names are VERIFIED as the item's `d1`/`d2`/`workable_servers` values, E3).
   231→   231→
   232→   232→**The two playback models are different, and CORS applies differently to each:**
   233→   233→
   234→   234→- **Native progressive MP4 (`PlaybackLink.type: 'video'` → `<video src>`).** A media element
   235→   235→  WITHOUT the `crossorigin` attribute fetches media in *no-cors* mode: cross-origin playback of a
   236→   236→  publicly accessible MP4 does **not** generally require CORS permission from the file host, and
   237→   237→  `<video>` seeking issues ordinary Range requests in that same mode. CORS permission becomes
   238→   238→  relevant for native playback only if the element carries `crossorigin` (needed for canvas/Web
   239→   239→  Audio capture of frames/audio). This is standard HTML media-element behavior, not an
   240→   240→  IA-specific fact — probe P2a verifies the HTTP-level preconditions against real IA responses
   241→   241→  rather than assuming them.
   242→   242→- **JavaScript-based playback (HLS via hls.js, DASH via dash.js/shaka, or any fetch/XHR-fed MSE
   243→   243→  pipeline).** The manifest and every segment are fetched from JS, so each request DOES require
   244→   244→  CORS permission (`Access-Control-Allow-Origin`) on the manifest and segment hosts. If IA HLS
   245→   245→  ever proves available, its viability would therefore depend on ACAO evidence (E16) — unlike
   246→   246→  native MP4 playback.
   247→   247→
   248→   248→**HLS availability (E18): UNKNOWN.** No official documentation of `.m3u8` playlists for item video
   249→   249→was captured. The provider therefore must **not** emit `type: 'hls'` links until a probe proves
   250→   250→otherwise; the initial link surface is progressive MP4 only.
   251→   251→
   252→   252→**Browser playback: NOT VERIFIED — and explicitly not claimable yet.** Nothing this session
   253→   253→proves: that a derivative file is fetchable and actually decodable (P2a/P2d), byte-range/206
   254→   254→seeking (P2b), the live redirect-chain shape (P2c), or that no special request headers are
   255→   255→required (P2e). A metadata 200 is metadata, not playback. Verification requires the §9.3 probes
   256→   256→plus, later, a real `<video>` test in Phase 4 on recorded fixtures first and live files second.
   257→   257→Until then the honest status is: **plausible (progressive MP4 via native playback), unverified.**

   280→   280→## 7. Rate limits, caching rules, timeouts, and error handling
   281→   281→
   282→   282→**Published numbers: none (E19 — UNKNOWN).** What IS published (E5, VERIFIED) is a conduct policy:
   283→   283→descriptive User-Agent mandatory; add delays between bulk requests; honor `429` + `Retry-After`;
   284→   284→cache responses to avoid repeats; use bulk endpoints; retry with exponential backoff. E12 shows
   285→   285→rate-limit introspection exists only for the Tasks API — not for search/metadata. Therefore our
   286→   286→plan is conservative by construction, and its numbers are OURS (recorded in D20, not attributed to
   287→   287→IA): identified UA string (`cloudstream-web/<version> (+https://github.com/smithP2007/CLOUDSTREAM)`,
   288→   288→which satisfies the E5 tool+version requirement), per-provider pacing ≥ 1 request/second sustained,
   289→   289→low concurrency (≤ 2), instant stop-and-backoff on any 429 honoring `Retry-After`.
   290→   290→
   291→   291→**Caching rules.** Official best practice is to cache (E5). Our machinery: engine response cache
   292→   292→(bounded LRU, honors `no-store`/`private`/`max-age`, never caches `set-cookie` responses — D18.6)
   293→   293→plus `LinkPipeline` TTL cache keyed `(scope, providerName, episodeId)` with the 20-minute default
   294→   294→mirroring the verified upstream link-cache behavior (D19). Credentialed links are never cached in
   295→   295→shared scope (D19) — moot for anonymous IA reads but the invariant stays. Proposed provider
   296→   296→defaults (ours): search responses 10 min, metadata 20 min, files-list handled inside metadata.
   297→   297→
   298→   298→**Timeouts.** Host defaults from `src/core/provider.ts` apply (search 15 s, load 20 s,
   299→   299→loadLinks 30 s — explicitly our values, UNKNOWN upstream, already documented there). The engine's
   300→   300→total-deadline abort + response byte cap (D18.6) bound any IA payload; metadata for large items can
   301→   301→be big, so the provider reads via the parse toolkit's size caps rather than unbounded strings.
   302→   302→
   303→   303→**Error handling mapping (provider-level, onto existing kinds):**
   304→   304→
   305→   305→| Condition | Mapping |
   306→   306→|---|---|
   307→   307→| Missing identifier (metadata returns `[]`, E3) | `load()` returns `null` — "nothing to return", not an error |
   308→   308→| Metadata response carries `error` field (E3) | `ProviderFailure.kind: 'validation'` when schema-rejected; `'provider'` when the provider surfaces it |
   309→   309→| HTTP 429 (+ `Retry-After`) | treated as rate-limited: fail with `'provider'` + backoff at caller level; engine does not auto-retry (documented) |
   310→   310→| HTTP 5xx / network faults | engine `HttpFailureKind` `'networkError'`/`'dnsFailure'` → host failure kinds `'provider'`/`'timeout'` respectively by the existing host classification |
   311→   311→| Timeout / caller abort | `'timeout'` / `'aborted'` (host-owned, D13) |
   312→   312→| Robots-gated path | `'robotsDisallowed'` (D18.9) — engine stays fail-closed on robots fetch failure. Current robots.txt finding (E24, owner-provided): visible wildcard rules disallow `/control/` and `/report/`; the API paths this provider uses are not visibly disallowed — to be RE-VERIFIED for our UA group in probe P1. robots.txt is not a substitute for the ToU review (§1, R1) |
   313→   313→| Schema drift (IA changes shape) | Zod failure → `'validation'`, item dropped and counted (D12) — observability events make drift visible |

   317→   317→## 8. Security requirements — what must not be proxied or fetched
   318→   318→
   319→   319→1. **Host allowlist (provider config, not a code change):** requests restricted to `archive.org`
   320→   320→   and `*.us.archive.org` datanode hosts (d1/d2/workable_servers pattern, E3). The D18 SSRF guard,
   321→   321→   DNS pinning, per-hop redirect re-validation, and fail-closed robots gate stay exactly as adopted;
   322→   322→   the provider adds a **narrower** destination policy on top, never a weaker one.
   323→   323→2. **No credentials in v1.** Anonymous read only. Never send `Authorization: LOW`, never hold IA
   324→   324→   login cookies (E4 describes both — we deliberately use neither). The D19 cross-user cache rule
   325→   325→   is retained as defense-in-depth.
   326→   326→3. **Never fetched:** lending / access-restricted items (E22) — enforced at query level (curated
   327→   327→   collection pools) AND item level (rights register §1 + metadata gate); identifiers absent from
   328→   328→   the per-item rights register; anything requiring login; the S3-like write API and
   329→   329→   Tasks API (E10/E12 — read/write surfaces we do not use); `.torrent`/magnet files; user-supplied
   330→   330→   URLs of any kind (the engine still accepts no client-controlled URLs — D18.1).
   331→   331→4. **No media relay in Phase 3.** Native `<video>` playback of public progressive MP4 is expected
   332→   332→   NOT to need a relay (§5); the Phase 4 authenticated, quota-capped relay (D8) remains the
   333→   333→   fallback for constrained sources (headers/CORS-dependent JS playback), never an open proxy,
   334→   334→   and is not built now.
   335→   335→5. **No execution of anything extracted** (D19): descriptions, page HTML, file names are DATA. The
   336→   336→   parse toolkit and static packer decoder are already the only processing paths; IA needs no
   337→   337→   unpacker at all (its APIs are JSON) — nothing in this provider may introduce `eval`/`new
   338→   338→   Function`/`node:vm`.
   339→   339→6. **Untrusted-content hygiene:** HTML fragments inside `description` are text-extracted server-side
   340→   340→   before display; poster/detail URLs are validated as http(s) by existing boundary schemas before
   341→   341→   use; non-http(s) link targets are never resolved (parse toolkit guarantee).
   342→   342→7. **Kill switch:** the provider ships wired through `wrapProvider` (D19) so it can be disabled
   343→   343→   instantly with a typed `ProviderDisabledError` — this is the POLICY §6 commitment made concrete
   344→   344→   for the first real provider.
