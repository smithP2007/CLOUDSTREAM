    51→## 1. Source authorization, API terms, and applicable content licensing
    52→
    53→**Policy mapping (roadmap checklist item 1).** The proposed provider serves content category
    54→**POLICY.md §3.1 (public-domain content)** and §3.2 (CC-licensed content), with the API itself falling
    55→under §3.4 ("services whose APIs and terms of service permit the intended use"). It matches the
    56→roadmap's Phase 3 build order #1 and the D3-approved initial source set. A new decision record
    57→(**D20**, §11) is required before any code.
    58→
    59→**What the Archive itself says about rights (E6, E7 — VERIFIED quotes):**
    60→
    61→- "The Internet Archive does not make guarantees as to the copyright status of items on archive.org
    62→  and cannot guarantee information posted on item details or collection pages regarding copyright or
    63→  other intellectual property rights."
    64→- The Terms of Use "require that users make use of the Internet Archive's Collections at their own
    65→  risk and ensure that such use is non-infringing and in accordance with all applicable laws."
    66→- For movies specifically: rights "vary from movie to movie but many of the films are licensed with
    67→  Creative Commons Licenses" (uploader-designated), and "Archive.org cannot guarantee the accuracy of
    68→  uploader-provided information."
    69→
    70→**Consequence for us (design constraint, not a claim):** item-level rights status is heterogeneous
    71→and uploader-asserted. The provider therefore cannot rely on "it is on archive.org" as a rights
    72→basis. It must operate on a **curated public-domain collection allowlist** plus an item-level
    73→rights-field gate (e.g. skip items that carry an explicit restricted-rights marker or a
    74→`licenseurl` pointing at a non-open license — the exact marker fields are INFERRED, to be pinned by
    75→fixtures per §9). The public-domain film list IA references (E7) is itself explicitly
    76→no-guarantee, so it may inform curation but cannot be a sole gate.
    77→
    78→**API terms for automated access (E5, E4 — VERIFIED):** the Archive publishes a Bots/LLMs/Automated
    79→Access policy requiring descriptive User-Agent identification and qualitative rate-limiting
    80→discipline (§7), and documents public, unauthenticated read access to metadata ("most information
    81→returned by Metadata Read is publicly available", E4). No clause prohibiting read-only API search or
    82→metadata retrieval for a client application was found in the official pages captured this session;
    83→the full current Terms of Use could not be captured (E20) and its archived dated copy is **action
    84→A1** — an explicit gate in §10, mirroring the roadmap rule that ambiguity must be resolved (or the
    85→provider does not ship).
    86→
    87→**Out of scope from minute one (POLICY §3 prohibitions, D7/D8):** lending / controlled-digital-lending
    88→items and any content requiring an archive.org account (E22), torrent/magnet delivery (excluded from
    89→our `PlaybackLinkType` v1), and any DRM-protected item (none exists in IA public video, but the gate
    90→is stated anyway).
    91→
    92→**Tag summary for §1:** authorization category VERIFIED (D3/POLICY); terms permitting read-only API
    93→use INFERRED-from-official-pending-ToU-snapshot (E20 gate); content licensing per-item
    94→UNKNOWN-with-mitigation (curated allowlist + rights gate).

   128→## 3. Example search results, item details, and metadata required by our TypeScript contract
   129→
   130→Our contract surface (from `src/core/`) that must be filled: `SearchResponse`, `SearchPage{items,
   131→hasNext}`, `LoadResponse` (movie variant: `MovieLoadResponse{dataUrl}`), `Episode{data, name,
   132→season, episode, posterUrl, description, date, runTime}`, `PlaybackLink`, `SubtitleFile`.
   133→
   134→**Search (advancedsearch `docs[]` → `SearchResponse`).** Planned mapping, INFERRED per-field until
   135→fixtures pin the exact response:
   136→
   137→| IA field | Contract field | Note |
   138→|---|---|---|
   139→| `identifier` | `url` (as `https://archive.org/details/{identifier}`) and `id` | provider-scoped detail URL, opaque to host |
   140→| `title` | `name` | may be missing → item skipped (D12 strict-but-shallow boundary) |
   141→| `mediatype:movies` + curated collection | `type` (`'Movie'` or `'Documentary'`) | decision: collections curated for single-work items |
   142→| `year` | `year` on details; optional on search | |
   143→| `description` | `plot` (details) | search-time description is often truncated HTML → stripped server-side via parse toolkit |
   144→| `creator` | `actors` (as `{name}`) on details | role info not supplied by IA |
   145→| `downloads` | not mapped | no contract field; could rank homepage rows later |
   146→
   147→`providerName` = `'InternetArchive'`; `posterUrl` = services/img endpoint (E15, INFERRED);
   148→`quality`/`score` left null (IA supplies no normalized 0–10 score — do not fabricate one).
   149→
   150→**Item details (`metadata` object → `MovieLoadResponse`).** Planned mapping: `metadata.title` →
   151→`name`; `metadata.year` (may be a range string like "1953" / "1953-1959" — parse defensively) →
   152→`year`; `metadata.description` → `plot` (HTML-stripped); `metadata.collection` (string or array) →
   153→`tags`; `metadata.runtime` (when present, format "HH:MM:SS") → `duration` in minutes; `licenseurl` →
   154→rights gate (not surfaced). `dataUrl` is a **provider-internal JSON blob** `{identifier, fileName}`
   155→naming the chosen derivative file (opaque per contract; mirrors the upstream pattern where
   156→`Episode.data` may be a JSON payload — verified upstream behavior, our docs §2.2).
   157→
   158→**Files list (`files[]` → playback candidates).** Each video-format entry contributes a candidate
   159→for `loadLinks`: `name` → file path; `format` → codec class (prefer "h.264" family per E8); `size`
   160→→ sanity cap; `length`/`height` (INFERRED fields) → quality number for `PlaybackLink.quality`.
   161→
   162→**Validation boundary.** Every payload crosses the Phase 2 boundary machinery: size-capped
   163→`JSON.parse` + Zod (`src/server/parse/json.ts`), non-coercive strict-but-shallow schemas (D12),
   164→drop-and-count on the link pipeline. The IA-specific quirk that **a missing item returns `[]`**
   165→rather than 404 (E3) means the metadata response schema is a union: full object OR empty array (→
   166→treated as `load(): null`).

   170→## 4. Item → movie / series / episode mapping in our data model
   171→
   172→IA's model (E3, VERIFIED): an **item** (identifier) is a directory of files with metadata; a
   173→**collection** groups items; there is no native "series/season/episode" object for movies.
   174→
   175→Planned mapping (INFERRED — a design decision for D20, not an IA fact):
   176→
   177→- **Item = one work.** A curated public-domain film item → `MovieLoadResponse` with a single
   178→  `dataUrl`. This is the v1 scope and the only mapping with an approved rights story (§1).
   179→- **Multi-part items (INFERRED, deferred):** some items contain several independently titled video
   180→  files (e.g. serial episode reels). The contract supports this as `TvSeriesLoadResponse` with one
   181→  `Episode` per playable file (`Episode.data` = the same JSON blob; `name` from the file's `title`
   182→  if present). This mapping is **not** in the initial scope; it is recorded here so the data
   183→  contract (opaque `Episode.data`) will not need to change if approved later.
   184→- **Collection = not a series object.** A collection (e.g. a curated PD set) can drive a homepage
   185→  row via scrape/advancedsearch, but we do **not** model collections as `TvSeriesLoadResponse`
   186→  bundles — IA collections mix works, are not ordered, and have no season/episode semantics.
   187→- **Anime/dub/live variants:** not applicable; IA provides none of these semantics for our curated
   188→  set. `tvTypes` for this provider = `['Movie', 'Documentary']` (constant, documented).
   189→
   190→Guard-rail: `Episode.data`/`dataUrl` stays opaque to the host (verified contract semantics);
   191→only the provider decodes it.

   195→## 5. Availability of direct MP4 / HLS playback URLs and browser-playback verification
   196→
   197→**What is verified (E8, E7):** IA generates **web-friendly h.264 MP4 derivatives** for video items
   198→("We will derive other file formats that are web-friendly such as h.264 mp4"), and the Archive's own
   199→help explicitly acknowledges that some files "simply can't be streamed" and fall back to download.
   200→So the officially documented playback path is **progressive MP4 (byte-range HTTP) of a derivative
   201→file** — which is exactly the `PlaybackLink.type: 'video'` shape our Phase 4 player maps to native
   202→`<video>`.
   203→
   204→**Direct URL form (INFERRED, E15):** `https://archive.org/download/{identifier}/{fileName}` for the
   205→h.264 derivative selected from `files[]`, likely 30x-redirecting to a datanode
   206→(`ia{NNN}.us.archive.org` names are VERIFIED as the item's `d1`/`d2`/`workable_servers` values, E3).
   207→
   208→**HLS (E18): UNKNOWN.** No official documentation of `.m3u8` playlists for item video was captured.
   209→The provider therefore must **not** emit `type: 'hls'` links until a probe proves otherwise; the
   210→initial link surface is progressive MP4 only.
   211→
   212→**Browser playback: NOT VERIFIED — and explicitly not claimable yet.** Nothing this session proves:
   213→CORS on the file host (E16), byte-range/206 behavior (E17), or that a given item's derivative file
   214→is actually fetchable and decodable. A metadata 200 is metadata, not playback. Verification requires
   215→the §9.3 probe plus, later, a real `<video>` test in Phase 4 on recorded fixtures first and live
   216→files second. Until then the honest status is: **plausible (progressive MP4), unverified.**

   237→## 7. Rate limits, caching rules, timeouts, and error handling
   238→
   239→**Published numbers: none (E19 — UNKNOWN).** What IS published (E5, VERIFIED) is a conduct policy:
   240→descriptive User-Agent mandatory; add delays between bulk requests; honor `429` + `Retry-After`;
   241→cache responses to avoid repeats; use bulk endpoints; retry with exponential backoff. E12 shows
   242→rate-limit introspection exists only for the Tasks API — not for search/metadata. Therefore our
   243→plan is conservative by construction, and its numbers are OURS (recorded in D20, not attributed to
   244→IA): identified UA string (`cloudstream-web/<version> (+https://github.com/smithP2007/CLOUDSTREAM)`,
   245→which satisfies the E5 tool+version requirement), per-provider pacing ≥ 1 request/second sustained,
   246→low concurrency (≤ 2), instant stop-and-backoff on any 429 honoring `Retry-After`.
   247→
   248→**Caching rules.** Official best practice is to cache (E5). Our machinery: engine response cache
   249→(bounded LRU, honors `no-store`/`private`/`max-age`, never caches `set-cookie` responses — D18.6)
   250→plus `LinkPipeline` TTL cache keyed `(scope, providerName, episodeId)` with the 20-minute default
   251→mirroring the verified upstream link-cache behavior (D19). Credentialed links are never cached in
   252→shared scope (D19) — moot for anonymous IA reads but the invariant stays. Proposed provider
   253→defaults (ours): search responses 10 min, metadata 20 min, files-list handled inside metadata.
   254→
   255→**Timeouts.** Host defaults from `src/core/provider.ts` apply (search 15 s, load 20 s,
   256→loadLinks 30 s — explicitly our values, UNKNOWN upstream, already documented there). The engine's
   257→total-deadline abort + response byte cap (D18.6) bound any IA payload; metadata for large items can
   258→be big, so the provider reads via the parse toolkit's size caps rather than unbounded strings.
   259→
   260→**Error handling mapping (provider-level, onto existing kinds):**
   261→
   262→| Condition | Mapping |
   263→|---|---|
   264→| Missing identifier (metadata returns `[]`, E3) | `load()` returns `null` — "nothing to return", not an error |
   265→| Metadata response carries `error` field (E3) | `ProviderFailure.kind: 'validation'` when schema-rejected; `'provider'` when the provider surfaces it |
   266→| HTTP 429 (+ `Retry-After`) | treated as rate-limited: fail with `'provider'` + backoff at caller level; engine does not auto-retry (documented) |
   267→| HTTP 5xx / network faults | engine `HttpFailureKind` `'networkError'`/`'dnsFailure'` → host failure kinds `'provider'`/`'timeout'` respectively by the existing host classification |
   268→| Timeout / caller abort | `'timeout'` / `'aborted'` (host-owned, D13) |
   269→| Robots-gated path | `'robotsDisallowed'` (D18.9) — note the engine's fail-closed posture on robots fetch failure; robots.txt for the API paths is itself a probe item (P1) |
   270→| Schema drift (IA changes shape) | Zod failure → `'validation'`, item dropped and counted (D12) — observability events make drift visible |

   274→## 8. Security requirements — what must not be proxied or fetched
   275→
   276→1. **Host allowlist (provider config, not a code change):** requests restricted to `archive.org`
   277→   and `*.us.archive.org` datanode hosts (d1/d2/workable_servers pattern, E3). The D18 SSRF guard,
   278→   DNS pinning, per-hop redirect re-validation, and fail-closed robots gate stay exactly as adopted;
   279→   the provider adds a **narrower** destination policy on top, never a weaker one.
   280→2. **No credentials in v1.** Anonymous read only. Never send `Authorization: LOW`, never hold IA
   281→   login cookies (E4 describes both — we deliberately use neither). The D19 cross-user cache rule
   282→   is retained as defense-in-depth.
   283→3. **Never fetched:** lending / access-restricted items (E22) — enforced at query level (curated
   284→   collections) AND item level (metadata gate); anything requiring login; the S3-like write API and
   285→   Tasks API (E10/E12 — read/write surfaces we do not use); `.torrent`/magnet files; user-supplied
   286→   URLs of any kind (the engine still accepts no client-controlled URLs — D18.1).
   287→4. **No media relay in Phase 3.** If the CORS probe (P2) shows file hosts do not allow cross-origin
   288→   playback, the answer is Phase 4's authenticated, quota-capped relay (D8) — not an ad-hoc proxy
   289→   now, and never an open one.
   290→5. **No execution of anything extracted** (D19): descriptions, page HTML, file names are DATA. The
   291→   parse toolkit and static packer decoder are already the only processing paths; IA needs no
   292→   unpacker at all (its APIs are JSON) — nothing in this provider may introduce `eval`/`new
   293→   Function`/`node:vm`.
   294→6. **Untrusted-content hygiene:** HTML fragments inside `description` are text-extracted server-side
